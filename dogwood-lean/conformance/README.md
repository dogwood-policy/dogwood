# Conformance against the crate

`conformance/run.sh` checks the specification against the `dogwood-language` crate in this repository. It compares validation: the specification's decision procedure for validity (`PolicySet.validationFindings`) reports what it finds by category, and the crate's validator must report findings in the same categories. It also compares decisions: it replays each bundle's traces with the verified evaluator (`Dogwood.Eval.authorize`) and with the crate's `Authorizer`. The bundles are the guide's examples, the crate's own test corpora, and the probes in `conformance/probes`, read from this checkout.

```bash
LEAN_CC=/path/to/cc dogwood-lean/conformance/run.sh
```

The run needs Cargo (with access to crates.io, through rustup's `stable` toolchain unless `RUSTUP_TOOLCHAIN` names another) and the Lean toolchain. Building the `conformance` executable compiles C with the compiler the Lean toolchain bundles. Where that compiler does not run, set `LEAN_CC` to another C compiler. On a host with an older glibc, for example, the bundled clang does not run. Once both builds are done, the run takes about forty seconds, most of it exporting the bundles.

The crate and the specification disagree in known ways (see "Validator and runtime gaps" below). `conformance/baseline.txt` lists every disagreement the run expects, and the run fails only on a disagreement the baseline does not list.

## How it works

1. `bridge/` is a small Rust program with a path dependency on `../dogwood-language`, built with the crate's `experimental-arithmetic` feature so that compound operands parse. It pins `cedar-policy` and `cedar-policy-core` to the release the Lean side builds on, and the script stops if the two disagree. For each bundle directory, the bridge builds the service and action schemas the way the crate's test harnesses do, and lowers the policy set. It reads a bundle's `providers.json` from the file, so that a `scriptFile` resolves against the bundle directory. Then it records one of two outcomes:
   - the stage at which the crate rejected the bundle; or
   - what the specification needs to validate and decide the bundle its own way, and what the crate did with it.

   For a lowered bundle, the bridge records:
   - **the typed event signatures** (`bridge/src/schema.rs`). A field of the spliced `input` or `output` group has the type the action's context declares at its path, and is required when every attribute along the path is. Any other field (`callerPrincipal`, `requestId`, …) has the type the event schema declares, and is optional; a pinned field must still be logged;
   - **the action schema**, read off the crate's augmented Cedar schema without the context attributes lowering hoisted (each temporal field `context.<id>`, and the `providers` record). It is the bundle's action schema with the enum entity types its provider declarations inject. The bridge writes it as Cedar's Rust validator stores it, with descendant information, and the harness inverts it to cedar-lean's ancestor form as cedar-lean's own protobuf decoder does;
   - **the provider declarations**, with each `paramType` converted to the Cedar type the crate gives the hoisted field (`ParamType::to_cedar_type_with`). A declaration whose argument or output type names an entity type the augmented schema lacks is left out, and so is a method whose type names one (the crate injects only the enums an invocation references);
   - **the rules**, each translated from its Cedar form, the policy JSON of `LoweredPolicySet::as_cedar`, into a rule of the specification. Each hoisted temporal attribute becomes the leaf it stands for, the authored leaf after macro expansion and pin injection, before the pin-relativization rewrite. Each hoisted provider attribute becomes the provider leaf of its invocation and output-method chain;
   - **every finding of the crate's `Validator`**, with its dialect code (`temporal`, `provider`, `cedar`), its message, and whether it is a warning;
   - **the decisions**. Each trace (`trace.log`, or `trace_*.log`) is parsed with the crate's `parse_trace`, and each event is translated into a timepoint. The crate's verdict at each event comes from a fresh `Authorizer` that ingests the trace in order, through `Authorizer::submit`: allow, deny, or no decision, with the errors its diagnostics report. The bridge also records whether the crate ingested each event: the crate rejects a history event that does not conform to the event schema, and fails a nonconforming decision event's decision closed, and it ingests neither. For a bundle with information providers, the bridge runs that `Authorizer` with a policy engine that records, at each decision event, the `context.providers` record the crate built. The crate takes each event's timestamp as given, in seconds, and the bridge exports it as recorded.

   The bridge writes each group of records to `conformance/out/<Group>.json`, as a JSON array of `Dogwood.Conformance.Case`s. It is a library (`bridge/src/lib.rs`) with a thin binary: a program that links the library can run the same export with a temporal engine of its own (`main_with(Some(factory))`, an `EngineFactory`), and each trace's `Authorizer` is then built with a fresh engine from the factory and `partition_temporal()`, so the decisions recorded are that engine's. The binary passes no engine, and its export is the crate's own. `Dogwood.Conformance.Json` defines the encoding and reads it back. Cedar sets and maps go through `Set.make` and `Map.make`, so they are well-formed whatever order the bridge writes them in.
2. `Dogwood.Conformance.Harness` compares a lowered bundle with the specification, on the policy set the bundle records (`Lowered.policySet`).
   - **Validation, by category.** `PolicySet.validationFindings` decides `PolicySet.Valid` (`Dogwood.Thm.validationFindings_eq_nil_iff`) and reports its findings by category (`Dogwood.Eval.Finding`). The harness sorts the crate's findings into the same categories by their messages (`crateCategory`). For each category, the two must report a finding together or not at all. An error finding of the crate that no category covers is a disagreement of its own. An impossible policy is a warning of Cedar's Rust validator and an error of cedar-lean's; the crate reports it as an error, and it counts in the `cedar` category on both sides. A crate finding with the code `context` (the Cedar part reads the request context whole, or reads an attribute lowering hoists) counts in the `contextRead` category.
   - **Decisions.** Each trace is replayed with `Dogwood.Eval.authorize` under the clamping reading, the crate's, over the trace an authorizer that stamps in nanoseconds builds from it: each recorded time, in seconds, is its event's clock reading in nanoseconds (`readingsOf`, `Trace.readings`), and each event is stamped with its reading, or one tick after the last stamp (`stampedOf`, `Trace.stamp`; `Dogwood.Thm.ingest_readings`). When the recorded times strictly increase, the stamps are the readings (`Dogwood.Thm.stamp_of_strictlyIncreasing`), and `Dogwood.Thm.authorize_scale` makes the replay in nanoseconds the replay in seconds the crate makes. `Dogwood.Thm.authorize_eq` proves the evaluator equal to `PolicySet.authorize` under a total reading, for a policy set whose leaves are safe. The verdict must be the crate's at every event, except where the specification fails a decision closed on nonconforming or missing data (a nonconforming decision event, request context, entity store, or provider output, or a scope entity a rule that applies reads but the event does not supply) that the crate decided: it allowed, or it denied without reporting an error. Such an event is a **runtime gap** of its kind, and the harness compares the verdict the specification gives on conforming data instead (`lenientOutcome`, which `Dogwood.Thm.decideWith_of_admits` relates to `PolicySet.authorize`), so the comparison of the temporal semantics is kept. Where the crate denied and reported errors, it failed too, and the two agree; where it allowed, the errors were a rule's (Cedar skips a rule whose condition errs), and it decided. A fail-closed outcome counts as a deny.
   - **Ingestion.** An event that does not conform to its signature is rejected at ingestion (`Rejection.nonconforming`). The specification's replay of a trace keeps the events the crate ingested, stamped (`replayIngested`): where the crate ingested the conforming events alone, that is what ingestion keeps (`Trace.conforming`, by `Dogwood.Thm.ingest_events`). The harness reports a nonconforming event that the crate ingested, and replays the conforming events alone, reporting the decisions a rejected event changed.
   - **Providers.** The replay of a decision reads its provider leaves off the crate's record at that decision (`providersAt`). Where the crate recorded nothing, every invocation fails, and the specification fails the decision closed (`FailClosed.providerError`).
   - **Stamping.** A trace whose recorded times do not strictly increase is reported apart, with three counts: the events the authorizer stamps one tick after the last stamp, how many of those the crate decided, and at how many events the verdicts differ. The crate takes the times as given, so on such a trace it decides over times the specification's authorizer would not assign; a verdict that differs there is a disagreement of stamping (`Disagreement.stamping`, keyed `stamping: <trace>@<event>`).
   - **Pins.** Every predicate of every exported leaf must carry the pins its event declares, because the crate exports the leaves after pin injection (`pinsCarried`).
3. The `conformance` executable (`Dogwood.Conformance.Main`, `lake exe conformance [--baseline FILE] [--write-baseline FILE] [--write-categories FILE] FILE.json…`) decodes each group, runs the comparison natively, and prints a report per group. Every disagreement has a key (`Disagreement.key`), and the baseline lists the expected ones as `<group> | <bundle> | <key>` lines. The checker exits with status 1 if a disagreement is not in the baseline, and with status 2 if a file cannot be read or decoded. `--write-baseline` writes the baseline that lists every disagreement of the run, to compare with the baseline in use. `--write-categories` writes, for each lowered bundle, one JSON line with the categories of each side's findings, and the crate's error findings.

`Dogwood.Thm.Formula.wellTyped_injectPins`, `Dogwood.Thm.Formula.isSafe_injectPins`, and `Dogwood.Thm.Formula.monitorsTime_injectPins` justify checking validity on the pin-injected leaves the crate exposes: pin injection keeps a valid leaf valid. `Dogwood.Thm.sat_injectPins_idem` justifies replaying them: the specification injects pins again, and injecting twice means the same as injecting once.

The script sets `RUSTUP_TOOLCHAIN` (to `stable`, unless it is set already) and `CARGO_TARGET_DIR` (to `bridge/target`), so the bridge builds with a rustup toolchain and a target directory of its own, whatever toolchain file or Cargo configuration the repository has.

## The probes

The crate's test corpora exercise few of the specification's rules and have no trace whose timestamps do not strictly increase, so `conformance/probes` adds bundles for both ([`probes/README.md`](probes/README.md) lists them).

## Generated runs

`conformance/gen-run.sh SEED COUNT` runs both harnesses on generated bundles. `conformance/gen/gen.py` writes them, in the layout above, each a function of the seed and its index alone (`gen.py --seed SEED --start I --count 1 --out DIR` writes bundle `I` again). It builds a random action schema (one or two namespaces, the root namespace, common types in the root or another namespace and the context as one, enumerated entity types, entity and action hierarchies, several principal and resource types, optional attributes, names that are not identifiers, types named like Cedar's), an event schema (the default, the unpinned one, or a random one: kinds, decision kinds, pins on the principal, the resource, a principal attribute or a context path, universal or not, nested records, `max_window` up to the limits of the clock), provider declarations with Rhai implementations (records, sets, enums, methods, field names that are not identifiers, and the declaration errors), macro definitions and libraries, rules from a typed, weighted grammar of temporal conditions and Cedar clauses, and traces with several principals, timestamps at the edges of the policies' windows, equal, decreasing and extreme timestamps, and nonconforming events. Its families aim at the validity rules (`nearmiss`: one near miss of a rule of `PolicySet.Valid`, or its accepted side), at each frontend stage's edge cases (`macros`, `schema`, `events`, `providers`), and at replay (`temporal`, `traces`). Each bundle's `meta.json` names its family and the features it uses.

`conformance/gen/run.py`, which the script calls, exports each chunk of bundles three times: with `--frontend`, in the default mode, and with the bridge's `partitioned` binary, which builds each trace's `Authorizer` with the crate's own temporal engine partitioned by the universal pins (`partition_temporal`). It runs `frontend-diff` on the first, and `conformance` on the other two, with the baselines of the repository; it finds by bisection a bundle on which the bridge fails or a harness runs too long. `conformance/gen/summarize.py` sorts every disagreement: by check, by kind, and, for validation, into one side accepting and the other rejecting (*verdict*) or both rejecting for findings of different categories (*categories*). It sets apart the kinds this README describes and the reporting differences listed in `known()`: a cascading finding of the crate (a literal of an undeclared entity type, an argument for a field group or an undeclared event, an undeclared path under an unguarded optional attribute, the inside of an ill-formed binder, a rule that admits no request environment), a stricter rule of the crate (a literal for a parameter of an unknown kind, a read of `context.providers`), and a read of a hoisted name by the Cedar part, which the bridge cannot show the specification (see below). The bundles, the exports and the summaries go under `$GEN_OUT`.

## What it cannot compare

The crate exposes no syntax tree for a condition it rejects while parsing, so rejected conditions cannot be compared. `Dogwood.Examples.Acceptance` restates the reference checker's own accept/reject unit tests (`extension/temporal/check.rs`) to cover that direction.

The validation comparison is by category, not by finding: two findings of one category in different leaves count as agreement. The crate's categories come from its messages, so a reworded message may need a new pattern in `crateCategory`.

The providers themselves are not compared: their outputs come from the crate's own evaluation of each decision, so the replay checks what the policies do with the outputs, that a decision fails closed when the crate's providers failed, and that the outputs conform to their declared types, but not the provider scripts, the argument resolution, or the conversion to declared types. Nor does it check that the providers are pure across decisions. The replay runs under the clamping reading only: the crate has no other, so the erroring reading (`ImplChoices.error`) is not compared. It compares the verdict only, not the determining policies or errors. And the bridge translates each rule from its Cedar form, so a defect shared by the crate's lowering and the bridge's translation would go unnoticed. In particular, a read by the Cedar part of a name lowering gives a leaf (`context.policy_0__temporal_0`) is, in the Cedar form, the reference to that leaf, so the specification sees the leaf where the author read an attribute; the crate rejects such a read (the probe `validation_context_read_own_leaf_name`, which the baseline lists), and the frontend harness's `validate` check compares that finding with the Lean port of the validator.

## Validator and runtime gaps

The baseline lists these disagreements:

- *A cascading Cedar finding* (`2085_provider_undeclared`, `2088_provider_method_undeclared`): for an invocation of an undeclared provider or method, the crate also reports a Cedar finding against the field it hoisted; the specification reports the provider finding alone.

The crate's validator enforces the specification's rules for optional attributes, pins on required paths, distinct `for` variables, and fields that bind a variable (`extension/temporal/validity.rs`), and types a binder over its own body only. It types each temporal leaf once per request environment of its rule, with entity types by their qualified names, records by their attributes, and `decimal` apart from `String`, and it checks action and `decimal` literals, binder types, wildcard operands, the arguments of the fields the event schema names, the aggregates inside compound operands, provider argument and method types exactly, impossible policies, the Cedar part's reads of the request context, and that no enumerated entity type is an ancestor (the schema's well-formedness); the probes `validation_*` of [`probes/README.md`](probes/README.md) show each. A policy set without leaves whose Cedar part reads the request context whole is accepted on both sides, as in Cedar, since lowering then adds nothing to the context (`readsContext` applies only to a policy set with a leaf). Its one permissive difference is an action schema that a previous lowering augmented for provider leaves, fed forward: its `providers` attribute refers to the shared provider type that lowering generated, and the crate extends that type, where `namesFresh` rejects the declared `providers`. No bundle has one. Its `Authorizer` makes the checks of `PolicySet.decideWith` in their order and rejects a nonconforming event at ingestion (`conformance.rs`), reads `principal.id` and `principal.type` as attributes, as the specification does, and does not order timepoints. It checks the strict mirror rule (`Mirrored`) as the specification does: a field that mirrors the request is absent when the event does not carry the request's value, so a scope-less event that logs a caller is rejected. Two differences remain:

- *Missing scope entities.* The crate adds a bare entity for the request's principal and resource when the event supplies none, without validating it, so a temporal leaf that reads an attribute of such an entity compares a value that does not resolve. The specification fails the decision closed when a rule whose scope holds has a temporal leaf that reads an attribute of a scope entity the event does not supply (`FailClosed.missingScopeEntity`): the probe `runtime_missing_scope_entity`, and `6007_arith_unresolved_attr_fail_closed` of the arithmetic corpus, whose traces supply no entity data for a leaf that reads `resource.coverage_limit`. On the outcome with the data supplied, the two agree.
- *Caller-stamped times, in seconds.* The crate takes each event's timestamp from the caller, in seconds, and accepts every event, whatever its time. The specification's authorizer stamps each event from its clock reading, in nanoseconds, one tick after the last stamp when the reading is not later. On the corpora, whose times strictly increase, the two decide alike. On the timestamp probes they decide over different times, and in `decreasing_timestamp_read` the verdicts differ: the specification stamps a `Read` recorded before the `Login` response one tick after it, and allows it, where the crate sees the response in the future, and denies.

## The frontend, stage by stage

`conformance/frontend-run.sh` compares the Lean frontend (`Dogwood.Frontend`, everything after the parsers) with the crate's, on the same bundle groups, one stage at a time.

```bash
LEAN_CC=/path/to/cc dogwood-lean/conformance/frontend-run.sh [--no-export] [--group G]… [--check NAME]… [--bundle TEXT] [--spans] [--diffs N]
```

1. The crate's off-by-default feature `frontend-export` adds `dogwood_language::frontend_export` (hidden from its documentation), which runs the lowering one step at a time on one bundle's sources and returns JSON of: the parsers' outputs as the frontend receives them (the surface policy set before the macro library is merged and macros are expanded, with every source span; the library's definitions; the event-schema DSL; the provider declarations before their check; the action schema as a Cedar schema fragment, its namespaces in Cedar's order); each stage's result, run on the results of the stages it depends on (the library merge, expansion, the array check, derivation, the event signatures, the universal pins, the decision kinds, cedarify, pin injection, the leaf encodings and revisions, augmentation, the providers' declarations, the compiled schema, the executable and the relativized leaves); and the outcome of the public pipeline on the same sources, with every component on which the stages disagree with it. A stage that fails records its error's category (the `api::Error` variant), message and span.
2. `bridge/ --frontend` writes that record for each bundle to `conformance/frontend-out/<Group>.json`, and adds what the comparison reads in the specification's types: each cedarified rule as a `Dogwood.Spec.Policy` that keeps the crate's names (`context.<id>`, `context.providers.<id>`), the base and the augmented schema as Cedar compiles them, and the bundle's record of the default export without its traces.
3. `lake exe frontend-diff` (`Dogwood.Frontend.DiffMain`) runs each check on each bundle: one stage of the Lean frontend on the crate's own inputs to that stage, compared with the crate's result, by their JSON encodings, without spans unless `--spans` is given, and, where a stage renames bound variables, up to that renaming (`renamed`). Errors agree when their categories agree and, for the crate's own messages, their messages. Two checks are end to end: `conformance` maps the crate's lowered set to the conformance record (`Lowered.toConformance`) and compares it with the bridge's, and `pipeline` runs `Frontend.lower` on the parsed inputs. `export` checks that the export's stages reproduce the public pipeline. A stage the Lean frontend does not compute yet is reported as not implemented, and a check whose inputs the crate did not produce (an earlier stage failed, or a parser rejected a source) as skipped. The files in `conformance/frontend-baseline/` list the expected disagreements, as `<group> | <bundle> | <check>` lines; the run fails on any other disagreement, and on a record that does not decode.

The frontend in one call (`Dogwood.Frontend.Pipeline`: `Driver.lowerAll`, `Driver.lowerManyAll`, from the parsers' outputs to the whole lowered set and the validator's findings) has checks of its own. The export also lowers a bundle with its stable ids (`ids.json`: `"annotation"` or explicit ids) and its distincter (`distincter.txt`), records each component of the crate's lowered set and of its identity (`outcome.lowered.full`: Cedar's policy JSON and text of each rule, the rule ids, spans, entries and revisions, the version hash, the augmented schema as Cedar's JSON, the leaves, the providers, the context reads), and exports several policy sets lowered together (`lower_many`) for a bundle with `many.json`. Four groups exercise them: `FrontendProbes` ([`frontend-probes/`](frontend-probes/README.md): every stable-id and distincter error, the multi-entry errors with the entry each belongs to, annotated schemas), and `ManyTemporal`, `ManyProviders` and `ManyMixed`, which the bridge makes from corpus bundles, two or three at a time (`--many K`). The checks are defined in `Dogwood/Frontend/Diff.lean` and `Dogwood/Frontend/Diff/Gaps.lean`.
