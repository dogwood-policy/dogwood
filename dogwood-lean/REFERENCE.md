# dogwood-lean: the detailed reference

This document is the detailed reference for the specification: its modules, its rules, its main theorems, and its known differences from the crate in this tree. [`README.md`](README.md) gives the overview.

The specification is written in Lean 4 and specifies Dogwood 1.2, the language that the `dogwood-language` crate next to this directory implements. It includes arithmetic in comparison operands (`+`, `-`, `*`), which the crate ships behind the off-by-default Cargo feature `experimental-arithmetic`. With the feature off, the crate rejects a compound operand at parse time. The specification describes the language with the feature on.

The specification builds on the Cedar formal specification, [cedar-lean](https://github.com/cedar-policy/cedar-spec/tree/main/cedar-lean), at release `v4.14.0`. That release matches the `cedar-policy` / `cedar-policy-core` 4.14.0 that the crate builds against. Dogwood reuses Cedar's values, entities, requests, operators, authorization algorithm, validator, and request and entity validation unchanged, and this specification reuses Cedar's definitions of them.

The semantics is **not executable**. Temporal conditions are given a satisfaction relation, in the style of metric first-order temporal logic, rather than an evaluation algorithm. A separate executable evaluator is proved to decide that relation for every safe condition (see [An executable evaluator](#an-executable-evaluator)). Parsing, macro expansion, and schema derivation are frontend work, and the specification starts from the frontend's output (see [Scope](#scope)).

The specification has three layers, and a soundness theorem that ties them together:

1. **Validity** ([Valid policy sets](#valid-policy-sets)): what validation requires of a policy set before an authorizer is built with it. The Cedar part is Cedar's own validator on the lowered rules; the temporal part is a typing relation and a safety relation, both declarative, with decision procedures proved equal to them.
2. **Runtime conformance** ([Runtime conformance](#runtime-conformance)): what the data a decision reads must be. A request, an entity store, a logged event, and a provider output each have a conformance rule, and a decision fails closed, with a reason of its own, on each kind of nonconforming data.
3. **Readings of out-of-range results** ([Readings of out-of-range results](#readings-of-out-of-range-results)): which readings of an out-of-range aggregate total or arithmetic result conform, and how a reading that reports errors decides. It fails closed exactly when the decision depends on how an erroring result would have been read.

[Soundness](#soundness) proves that, for a valid policy set and conforming data, every rule evaluates to a `Bool` or a runtime error, the decision is Cedar's on the lowered rules, no comparison the response depends on has an operand that does not resolve, and every witness and aggregation row is typed.

Besides the meaning of a decision, the specification states what every implementation of the language must do around it. An implementation stamps every event it accepts with a timestamp of its own, after the last, and rejects an event that does not conform to the event schema ([Ingestion](#ingestion-stamping-and-conformance)). It gives rules deployed while events flow one of two meanings ([Policy updates](#policy-updates)). It presents one totally ordered log to every submitter and instance ([The event-log contract](#the-event-log-contract)). Where the language leaves a choice to an implementation, such as how to read an out-of-range result or which reading of a policy update to give, the specification is parameterized over the choices it admits. It also exports general lemmas for proving an implementation correct against it ([Lemmas for proofs of implementations](#lemmas-for-proofs-of-implementations)).

## Building

The specification is a Lake project. It needs the Lean toolchain named in `lean-toolchain` (`leanprover/lean4:v4.34.0`), installed through [elan](https://github.com/leanprover/elan). Run Lake from this directory:

```bash
cd dogwood-lean
lake build
```

The first build fetches cedar-spec `v4.14.0` and Batteries `v4.34.0` from GitHub, then checks the Cedar modules this specification imports. Afterwards, `lake build` checks the default library `Dogwood`, which holds everything but the conformance checker's modules (`Dogwood.Conformance.*`, the library `DogwoodConformance`) and the executables' main modules.

This directory is not a member of the package's Cargo workspace, and a default Cargo build needs no Lean toolchain. `vendor/` holds the cedar-lean and Batteries modules that the specification (`Dogwood`, with its proofs and examples) and the Lean frontend import, at the revisions `lake-manifest.json` pins. When the crate's off-by-default `lean-frontend` feature builds the frontend from source, it takes these modules from the Lean project's `.lake/packages` if they are there, and from `vendor/` otherwise, without network access. The crate's test `lean_vendor`, which every `cargo test` runs, checks `vendor/`. After a change of the pinned revisions or of the specification's or the frontend's imports, regenerate it with `scripts/vendor_deps.py write`.

### Keeping Cedar aligned

The Lean side and the Cargo side must describe the same Cedar release. `lakefile.lean` requires cedar-spec at the tag `v4.14.0`. `bridge/Cargo.toml` pins `cedar-policy` and `cedar-policy-core` to exactly `4.14.0`, the release the in-tree crate requires. `conformance/run.sh` stops with an error if the version the bridge resolved differs from the cedar-spec tag. When the crate moves to a new Cedar release, bump all three together, and regenerate `vendor/`.

## How the specification is organized

### Conditions are Cedar expressions with two extra leaves

A Dogwood rule is a Cedar static policy. Its `when` / `unless` clauses may contain two kinds of leaf that Cedar cannot express. A *temporal leaf* is a `temporal { … }` marker, either as a whole clause or inline in a Cedar expression. A *provider leaf* is an information-provider invocation, `Ns::Fn(args)` with its output-method chain.

`Dogwood.Spec.Expr` is `Cedar.Spec.Expr` extended with exactly these two constructors. `Dogwood.Spec.evaluate` is `Cedar.Spec.evaluate` case for case. Every Cedar operator is delegated to Cedar's own definition. A leaf evaluates to the value a *leaf valuation* `θ` assigns it: a temporal leaf to a `Bool`, and a provider leaf to the provider's output. The per-request authorizer mirrors `Cedar.Spec.isAuthorized` definition for definition.

The reference implementation lowers each leaf to an attribute of `context` (`context.<id>` for a temporal leaf, `context.providers.<id>` for a provider leaf) and fills that attribute at decision time. The decision semantics gives each leaf its value directly, so no attribute names are involved there. Validation does lower the rules, to run Cedar's validator on them (see [Valid policy sets](#valid-policy-sets)), and `Dogwood.Thm.evaluate_lower` proves that the lowered rules evaluate as the rules do.

### Temporal conditions have a satisfaction semantics

`Sat ι rate σ e vis v j φ` states that the temporal condition `φ` holds at timepoint `j` of trace `σ`, whose timestamps count ticks of the clock rate `rate`, under valuation `v`, for a decision made at event `e`. It is defined by recursion on `φ`.

In mathematical notation, write v, j ⊨ φ for `Sat ι rate σ e vis v j φ`. Five things are fixed for a whole decision and left implicit: the trace σ, the decision event e, the set V of visible timepoints (`vis`, see [Key-local semantics is a visibility predicate](#key-local-semantics-is-a-visibility-predicate)), the rate, and the reading ι of out-of-range results. Write τ_j for the timestamp of timepoint j, e_j for its event, and L_j for its logged record. The window looks back by timestamp, closed at both ends: k ∈ W_w(j) iff 0 ≤ τ_j − τ_k ≤ ‖w‖, with ‖w‖ the window's length in ticks (see [Time is counted in ticks](#time-is-counted-in-ticks)).

```
v, j ⊨ φ && ψ               iff  v, j ⊨ φ  and  v, j ⊨ ψ
v, j ⊨ !φ                   iff  not v, j ⊨ φ
v, j ⊨ formerly within w φ  iff  some k ≤ j in V ∩ W_w(j) has  v, k ⊨ φ
v, j ⊨ previous within w φ  iff  the last k < j in V is in W_w(j), and  v, k ⊨ φ
v, j ⊨ φ since within w ψ   iff  some k ≤ j in V ∩ W_w(j) has  v, k ⊨ ψ,
                                  and  v, k' ⊨ φ  for every k' ∈ V with k < k' ≤ j
v, j ⊨ a::κ{ fᵢ: tᵢ }       iff  e_j has action a and kind κ, and for each i, L_j has a value
                                  at fᵢ, and tᵢ is * or ⟦tᵢ⟧ = L_j(fᵢ)
v, j ⊨ t₁ ⋈ t₂              iff  t₁ and t₂ denote c₁ and c₂ at j, and  c₁ ⋈ c₂
v, j ⊨ exists (x: T). φ     iff  v[x ↦ u], j ⊨ φ  for some value or timepoint u
v, j ⊨ tp(x)                iff  v(x) is the timepoint j
```

These clauses make the following choices:

- **Windows include the present.** `formerly` and `since` consider k = j, so `formerly within 1h P` holds when the decision event itself matches P. `previous` never considers j.
- **Windows are measured by timestamp, the order by position.** "The previous timepoint" is the previous visible position, and the window then checks its timestamp.
- **A predicate at the top of a leaf is about the decision event.**
- **Request-side terms always mean the current request.** `context.*`, `principal`, and `resource`, with attribute paths, denote values of the request being decided at every past timepoint an operator scans. A past event's fields can be read only through a predicate's arguments.
- **A mentioned field must be present.** `P{ f: * }` requires the logged record to have the field f.
- **Predicates and `tp` test variables; they do not bind them.** Only `exists` and a `for` list bind. In `exists (x: Long). (P{ f: x } && x > 5)`, the existential chooses the value the field holds. A timepoint is observed only through equality: it may be compared with a timepoint, and it keeps aggregation rows distinct.
- **A predicate does not consult V.** Only the temporal operators restrict themselves to the visible timepoints.
- **`exists` ranges over all values and all timepoints** (`TVal`). The declared type is read by validation only. On safe conditions, finitely many candidate values read off the trace and the request suffice (`sat_exist_iff`).
- **An operand that denotes nothing makes its comparison false.**

An aggregate's rows are the satisfying assignments of its `where` body to its `for` domain. `count` is the size of that set and `sum` adds a column of it. A set without a finite size has no total.

A compound operand `l ⊕ r` (`+`, `-`, or `*`) denotes the result of `⊕` on two integers that `l` and `r` denote. The exact result is read through `ImplChoices` when it lies outside the `Long` range (see [Readings of out-of-range results](#readings-of-out-of-range-results)), once per operation, so a nested compound sees its operands' readings. When an operand denotes no integer, the compound denotes nothing. An aggregate may be a leaf of a compound, as in `(sum …) + context.input.amount <= 100`.

The semantics is total: it gives a meaning to every condition, including ones validation rejects. For a valid condition over conforming data, under a total reading, at a decision that passes its checks, the cases where an operand denotes nothing, where an `exists` witness or a row has the wrong type, and where an aggregate has no total do not arise ([Soundness](#soundness)).

### Time is counted in ticks

Timestamps are integers that count ticks of the authorizer's clock. `TickRate` declares how many ticks make up a second, and a policy set carries its authorizer's rate (`PolicySet.tickRate`), nanoseconds by default (`TickRate.nanos`). A window keeps its authored units, an amount and a unit (`within 1h`), and the semantics compares it in ticks: `InWindow` requires `0 ≤ ts(j) − ts(k) ≤ w.ticks rate`, the window's length in seconds times the rate. `Formula.horizon` and `PolicySet.horizon` are in ticks too. The `max_window` cap (`PolicySet.maxWindow`, `defaultMaxWindow`) bounds a window's authored length, in seconds, as the crate's validator checks it, so validity does not depend on the rate.

The rate is a declared parameter rather than nanoseconds directly, so that a proof of an implementation can count time at the rate the implementation uses: an implementation may stamp in nanoseconds while its monitor runs at another configured rate. `Dogwood.Thm.sat_scale` proves that counting at a rate `c` times finer, with every timestamp multiplied by `c` (`Trace.scale`), changes no truth value, and `authorize_scale` that it changes no decision; `Formula.horizon_mul` scales the horizon. So a proof at one rate holds at every multiple of it, and the meaning of a trace recorded in whole seconds does not depend on the unit. Stamping does depend on the rate (see [Ingestion](#ingestion-stamping-and-conformance)): an event stamped one tick after the last is a nanosecond late at nanoseconds, and a whole second late at one tick per second, which adds a second that did not pass. That is why the default is nanoseconds.

### Key-local semantics is a visibility predicate

A pin is *symmetric* when it is pinned to the current request's principal, its resource, or a context attribute (`pin f = principal`, `pin f = resource`, `pin f = context.q`), whatever the field is called (`EventSchema.Pin.isSymmetric`), and *universal* when every signature declares it identically. When the event schema declares a universal symmetric pin, the guide specifies key-local semantics: a temporal leaf behaves as if the trace contained only the events that agree with the current request on the pinned fields. The default event schema declares such a pin, on `callerPrincipal`. The reference implementation realizes this by rewriting each leaf (`event_schema/relativize.rs`).

This specification states key-local semantics directly. `Sat` takes the set of visible timepoints, `vis`, as a parameter. `EventSchema.Visible` makes every timepoint visible when there is no universal symmetric pin. Otherwise it makes visible exactly the events that are *mine*: events of a declared signature that agree with the request on every universal symmetric pin. Timepoint indices remain global, as in the rewrite. Only equality observes an index, so renumbering them changes nothing (`Dogwood.Thm.sat_subseq`).

`Dogwood.Thm.Frontend.relativization_correct` proves that the frontend's port of the rewrite (`Dogwood.Frontend.LeafPasses.relativize`) agrees with key-local semantics on traces whose timestamps strictly increase. The frontend comparison checks that the port agrees with the crate's rewrite on every leaf it compares. Its output has a disjunction (μ, "an event of mine") and orders timepoints by position, so it is read under an extension of `Sat` with both (`LeafPasses.RSat`). The theorem (`LeafPasses.RelativizationTheorem`) says: for a well-typed, safe leaf, over a derived event schema that agrees with the policy set's, on a trace whose timestamps strictly increase and whose length fits a `Long`, the relativized executable leaf with every timepoint visible holds at a decision exactly when `PolicySet.LeafHolds` does. Its core, `rsat_relCond`, needs only timestamps that never decrease: then every event of the key between an event in a window and the window's end is in the window too, so the rewrite's `previous` and `since`, which consider the key's events inside the window, see what the specification's see. The rest of the proof shows that the guard μ is visibility (`xsat_mu_iff_visible`), that a body which implies mine holds only at the key's events (`xsat_mine`), that the executable form of a well-typed leaf is the leaf itself (`unorderFree_of_typed`), and that ordering timepoints by position changes nothing on a well-typed, safe leaf (`xsat_ord_iff`). The length bound makes the counts of the `since` encoding `Long`s, so that no reading of an out-of-range count can make two different counts equal. The leaf's own names need no hypothesis: the rewrite draws its binders' names with a prefix no variable of the leaf starts with (`LeafPasses.freshPrefix`, `noFreshNames_freshPrefix`).

An implementation may instead keep one log per partition key, and decide each event over its own key's log. `Dogwood.Spec.Partitioned` defines this **partitioned evaluation**. Each key's log is stamped on its own: an event's stamp is its reading, or one tick after the stamp of the last event of its own key's log when the reading is not later. A leaf's value at a decision (`PolicySet.PartLeafHolds`) is `Sat` of the pinned leaf over the decision's key's log, stamped on its own, at the decision's position, with every timepoint visible, and `PolicySet.authorizePart` is the decision with those values. Without a universal symmetric pin there is one key, and the partitioned decision is `PolicySet.authorize` over the stamped stream (`authorizePart_eq_authorize_of_noPins`). With one, the two agree when the clock readings strictly increase across a whole stream of conforming events (`authorizePart_eq_authorize`, `partitionable_of_strict`), and can differ otherwise. In `Dogwood.Examples.PartitionedStamps`, an event that arrives with the same clock reading as the last event of another key is stamped one tick later in the single log than in its own key's log.

### Valid policy sets

`PolicySet.Valid P` (`Dogwood.Spec.Validity`) is what validation requires. A policy set carries its rules, the derived event schema, the action schema as Cedar's validator reads it (`Cedar.Validation.Schema`, with the enum entity types the provider declarations inject), the `max_window` cap, the provider declarations, and the names the action schema declares `external`.

**The Cedar part.** Lowering replaces each leaf by an attribute of the request context: a temporal leaf by a `Bool` attribute, a provider leaf by an attribute of its declared output type (`PolicySet.lowered`). The augmented schema adds each attribute, required, to the context record type of the actions the leaf's rule can apply to: those its action scope admits (`PolicySet.augmentedSchema`, `PolicySet.targetedAt`, `actionScopeAdmits`). This is the crate's augmentation (`scope_target_actions`), which keeps the schema small, up to two differences that change no verdict: the crate gives every action a provider rule reaches the whole shared `providers` record (holding every provider output), and leaves out pure action groups, which have no request environment. Adding the attributes to more actions is safe: validation against any augmentation that adds each leaf's attribute at least to those actions, and adds only leaf attributes (`PolicySet.Covers`), gives the same verdict (`Dogwood.Thm.valid_iff_covers`), and in particular against the schema that adds every attribute to every action (`PolicySet.allAugmentedSchema`, `Dogwood.Thm.valid_iff_validAll`). The proofs about a valid set's decisions use that form, since a decision's augmented request context holds every leaf's value. Validity requires:

- every leaf has a type, the leaves' attribute names are distinct, and no action's context declares one of them;
- the Cedar part reads `context` only through attribute accesses and `has` tests of other attributes (`Expr.ReadsContext`), so that the lowered rules evaluate as the rules do on the augmented request (`evaluate_lower`), when the policy set has a leaf. A policy set without leaves is its own lowering, the augmented request is the request (`augmentRequest_of_nil`), and its rules may read `context` whole, as in Cedar (`evaluate_lower_self`, `isAuthorized_lower_self`);
- the augmented schema is well-formed (`Cedar.Validation.Schema.validateWellFormed`), which Cedar's soundness theorem assumes;
- no entity type of the augmented schema has an enumerated entity type as an ancestor, in each request environment (`Schema.standardAncestors`). Cedar 4.14 allows an enumerated ancestor, and Dogwood does not: the crate's validator rejects one;
- the action schema declares no name `external` when the policy set has a rule (`complete`): Cedar 4.14's validator validates no policy against an incomplete schema (RFC 116). `PolicySet.externalTypes` and `PolicySet.externalActions` hold the external names; `actionSchema` holds Cedar's view of them, an entity type without attributes or tags and an action that applies to no principal and no resource, so that a value of an external entity type may have any id and no request for an external action conforms;
- Cedar's validator accepts the lowered rules against the augmented schema (`Cedar.Validation.validate`).

The crate checks the same requirements against its own augmentation (`scope_target_actions`, `cedarify/schema_augment.rs`). That its target actions are the actions `PolicySet.targetedAt` gives, up to the two differences above, is not proved. The frontend differential compares the two augmented schemas. The Cedar part has no typing of its own.

**The horizon.** When the event schema declares `max_horizon` (`PolicySet.maxHorizon`, in seconds; `none` by default, no cap), every temporal leaf's horizon (`Formula.horizon`, at one tick per second: a `formerly` or `previous` adds its window to its body's, `since` its window to the larger of its sides', and conjunction, negation, `exists` and comparisons take the largest of their parts') is at most it (`PolicySet.Valid.horizon`). The crate checks the same sum, exactly. Its event-schema parser also resolves the window cap (`max_window` defaults to a declared `max_horizon`, else 24h) and rejects a `max_window` longer than a declared `max_horizon`. The frontend port resolves the caps the same way and rejects the same pair, with the same message, when it derives the event schema (`Dogwood.Frontend.Derive.limits`); the crate rejects it earlier, when it parses the event schema.

**The temporal part.** Every temporal leaf is valid at its position (`PolicySet.LeafValid`): well-typed in every request environment its rule's scope admits (`PolicySet.envsOf`), with the facts its position establishes; safe; and every monitoring scope of it varies with the timepoint. A rule's scope admits an environment when its action scope admits the action, and its principal and resource scopes admit the environment's principal and resource types (`scopeAdmitsType`). Under `in E`, those are `E`'s type and the types the schema lets be in it (`Schema.memberOfType`, Cedar's `TypeEnv.descendentOf`), as Cedar's typechecker narrows `in`: on an entity store that conforms to the schema, no other entity is in `E` (`scopeAdmitsType_of_eval`).

*Typing* (`Formula.WellTyped C Γ φ`, `Dogwood.Spec.Temporal.Typing`). A term has a Cedar type, or is a timepoint. The rules:

- **Binders.** Every `exists` binder and `for` variable has a meaningful declared type (`Long`, `String`, `Bool`, `decimal`, `Timepoint`, or a declared entity type), and is not named after a Cedar request variable. The `for` variables of one aggregation are distinct. A variable is used only where it is bound, so the condition is closed.
- **Comparisons.** Ordering applies only to two `Long`s. Equality applies to two terms of the same type, including two `decimal`s and two timepoints; two entities of different types may be compared, unless the equality has the shape of one that can bind a variable: a bare variable on one side, and on the other a term that is neither a variable nor a wildcard nor a compound holding one (`eqRestricted?`), under `==` or `!=`, whether or not the variable is already bound. A wildcard is not a comparison operand.
- **Extension types.** Temporal conditions do not support Cedar's extension types other than `decimal`: no request-side path a term reads, and no pin's, has a type that is or holds a `datetime`, a `duration`, or an `ipaddr` (`CedarType.temporalSupported`). A predicate that leaves such a field out, or matches it with a wildcard, is well-typed. The decision procedure reports such a path in its own category (`Finding.extension`).
- **Arithmetic and aggregates.** Every atom of a compound operand is a `Long`, and so is an aggregate. A `sum`'s summand is a `Long` binder of its own `for` list.
- **Predicates.** A predicate names a declared event signature, and each argument a declared field of it. A variable argument has a type every value of the field has; any other argument a type the field can hold. No argument is an aggregate or a compound. Every pin of the signature correlates its field with a request-side path that is required in the environment, of a type the field can hold.
- **Request-side paths.** A `context.<path>` resolves in the environment's context record type, and `principal.<path>` / `resource.<path>` in the attributes of the scope entity type. `id` and `type` are attributes like any other, as in Cedar. Every optional attribute along a path is guarded: the Cedar part tests it with `has` at the leaf's position (`Expr.leafFacts`), as in `context.input has amount && temporal { … context.input.amount … }`.
- **Literals and windows.** An entity literal names a declared entity or an action; a `decimal` literal parses. Every window is positive and at most `max_window`, a cap on its authored length in seconds.

*Safety* (`Formula.Safe R φ`, `Dogwood.Spec.Temporal.Safety`). A positive atom restricts a variable: a predicate argument `P{ f: x }`, `tp(x)`, and a binding equality `x == t` whose value side is not a variable or a wildcard, provided the variables of `t` are restricted. Within a `&&` chain the restricted variables are a least closure (`Formula.Restricts`), the same however the conjuncts are ordered. A condition is safe when every conjunct reads only restricted variables, a negation and the left operand of `since` read only variables restricted outside them, every `exists` variable is restricted by its body, and every `for` variable by its `where` body. The closure is least, so a cycle restricts nothing: `count for (x: Long), (y: Long). where (x == y + 1 && y == x - 1)` is unsafe (`Dogwood.Examples.Acceptance.circular`). This is the safe-range analysis of metric first-order temporal logic, extended with equalities whose value side computes from restricted variables.

*Monitoring scopes* (`Formula.MonitorsTime`). Every top-level conjunct, temporal-operator body, operand of `since`, `exists` body, and `where` body varies with the timepoint. This rule has no semantic consequence; it rejects conditions that are almost always mistakes.

**The provider part.** Every provider leaf names a declared provider and declared output methods, each method taking the value the stage before it produces (`Provider.Call.Declared`), and its arguments have their declared types in every environment the rule admits (`Provider.Call.TypedIn`). A request-path argument has its declared type (`Provider.Arg.typeIn?`), and an optional attribute along it needs no `has` guard: the provider contract tolerates an absent argument, and an attribute the request lacks resolves to one (`Provider.Arg.resolve`).

**Deciding validity.** `PolicySet.validationFindings P` lists the categories of the problems it finds, none exactly when `P` is valid (`Dogwood.Thm.validationFindings_eq_nil_iff`). It is built from `Eval.safeB` (`safeB_iff`), `Formula.check` (`Formula.check_eq_nil_iff`), `Formula.monitorsTimeB` (`monitorsTimeB_iff`), and cedar-lean's executable validator. Pin injection keeps a valid leaf valid (`Formula.wellTyped_injectPins`, `Formula.isSafe_injectPins`, `Formula.monitorsTime_injectPins`).

**Where validity differs from the crate's validator.** The conformance run compares the two by category (see [Conformance against the crate](#conformance-against-the-crate)). Apart from where it adds hoisted attributes, the crate's validator enforces the rules above: it types each leaf once per request environment, with entity types by their qualified names, records by their attributes, and `decimal` apart from `String`; it checks literals, binder types, and the fields the event schema names; it types provider arguments exactly; it reports an impossible policy as an error; and it rejects a Cedar part that reads an attribute lowering hoists, or, in a policy set with a leaf, reads the request context whole. A policy set without leaves may read the request context whole on both sides, as in Cedar, since lowering then adds nothing to the context. The specification is more permissive in a few ways: safety is a closure, while the reference checker (`extension/temporal/check.rs`) walks each `&&` chain left to right and rejects `x > 0 && P{ f: x }`, which is safe; and the crate requires an entity type a provider declaration names to be an enum.

### Runtime conformance

The data a decision reads must conform to the schemas validation checked the rules against (`Dogwood.Spec.Conformance`):

- **The request** conforms when Cedar's `validateRequest` accepts it against the action schema: its principal, action, and resource are of a request environment's types, and its context is an instance of the action's context record type, with every required attribute present and no undeclared one.
- **The entity store** conforms when Cedar's `validateEntities` accepts it. A decision's store is the schema's action entities followed by the entity data supplied with the event (`PolicySet.decisionEntities`); the schema's entities take precedence, so supplied data cannot change the action hierarchy. The request's principal and resource need not be in the store; in the Cedar part, an attribute read of an absent entity is Cedar's `entityDoesNotExist` error, one of the runtime errors validation cannot rule out.
- **The scope entities a temporal leaf reads** must be supplied, for the rules whose scope holds at the request (`PolicySet.scopeEntitiesSupplied`, see [Scope entities a leaf reads](#scope-entities-a-leaf-reads)).
- **An event** conforms when it is of a declared signature and its logged record is an instance of it (`Event.Conforms`): every logged declared field has its declared type, every required field and every pinned field is logged, and every field that mirrors the request follows the **mirror rule** (`Mirrored`). The mirrored fields (`EventSignature.mirrors`) are the fields of the pins to the request's principal, its resource, or a context attribute, whatever the field is called (`EventSchema.Pin.isSymmetric`), and `callerPrincipal` and `callerResource` when no pin names them. The rule is strict: when the event carries the request-side value (its principal, its resource, or the pinned context attribute), the logged field holds exactly that value; when the event does not carry it, the field is absent. The mirror rule is what lets a pin isolate a key: an event can neither log one principal as its caller while it carries another, nor log a caller while it carries none. Its logged record and its context are **canonical** (`Canonical`, `Dogwood.Spec.Canonical`): every set in them is well-formed, sorted and without duplicates as `Set.make` builds it, and so is every record's attribute map.
- **A provider output** conforms when it is a value of the provider's declared output type (`Provider.Output.Conforms`).

`principal.id` and `principal.type` (and the same for `resource`) are the attributes named `id` and `type` in the entity data the event supplies (`Event.entityAttr?`), as in Cedar: they are not the uid's id and type name, and validation rejects them where the entity type declares no such attribute.

**Every event carries the scope of the key it reports on.** Under a universal symmetric pin, every signature pins the field, so every conforming event logs it, and by the strict mirror rule it logs it only when it carries the request-side value: a conforming event always carries its key's scope. A history event with no principal (a scope-less `Login::response`, say) does not conform under the default event schema, whose pin `callerPrincipal = principal` is universal, whether or not it logs a `callerPrincipal`: with the field it breaks the mirror rule, and without it the pin. It is rejected at ingestion, so no decision sees it. A submitter that records history for a key therefore attaches the key's scope to it, as `Event::from_request` does for a decision event. Two consequences follow:

- **No forged history.** If the mirror rule held whenever the request side did not resolve, a scope-less event could log `callerPrincipal: alice` and enter Alice's history: Mallory could fill Alice's rate limit, or pass a two-person rule with two scope-less approvals claiming other approvers. When the pin is declared on some signatures and not others, it is not universal, but pin injection still compares the logged field with the decision's principal, so the forgery would work there too. The strict rule rejects every such event.
- **Cross-principal evidence is key-local.** An event is evidence only for the key whose scope it carries, so an administrator's revocation of Alice's access is the administrator's event, and Alice's rules do not see it under a universal pin. A rule that must see another principal's events needs an event schema without a universal pin on those events.

`Dogwood.Thm.partitionable_of_strict` states the first consequence for partitioned evaluation: every trace of conforming events is `EventSchema.Partitionable`, so keying events by their logged pin fields, or by their own request-side values (`fileable_of_strict`, `mine_iff_mineReq_of_strict`), computes key-local visibility.

**Canonical values.** Cedar's `instanceOfType` admits a set held out of order or with repeated elements, which is then a different value from the same set in order, and compares unequal to it: `{"a", "b"}` held as `["b", "a"]` would make a pin or a comparison over the field tell two spellings of one set apart. Conformance therefore requires canonical values, and on canonical sets equality is equality of members (`Dogwood.Thm.canonical_set_eq_iff`). The two other ways an implementation's values can have several spellings have none here: Cedar values have no `null`, so a field an implementation records as `null` is absent (the bridge drops such fields), and a decimal is its numeric value, so `02.5` and `2.5` are one value. An implementation therefore canonicalizes before it checks an event: it sorts and deduplicates sets, drops `null` fields, and compares decimals by value (`canonical_set_make` and `canonical_record_make` show that `Set.make` and `Map.make` produce canonical values). The request's own conformance is Cedar's `validateRequest`, unchanged; the canonical-context requirement is part of event conformance, which a decision checks first.

Values are checked with Cedar's `instanceOfType`. Cedar defines it by well-founded recursion, which the kernel cannot evaluate, so `Dogwood.Eval.valueInstanceOf` restates it structurally (`valueInstanceOf_eq`), and the Boolean checks built on it decide each relation (`conformsB_iff`, `requestConformsB_eq`, `output_conformsB_iff`). The worked examples use them to prove their decisions by `decide`.

### Decisions over traces

`PolicySet.authorize ι P ω σ n` is the outcome of ingesting the event at timepoint `n` of the trace `σ`. It follows guide chapter 8, §6. Every decision makes the same checks, in this order (`PolicySet.decideWith`):

1. an event of a kind the schema does not mark `decision` produces no response;
2. a decision event without a principal, or without a resource, fails closed (`noPrincipal`, `noResource`);
3. a decision event that does not conform to its signature fails closed (`nonconformingEvent`);
4. a request that `validateRequest` rejects fails closed (`nonconformingContext`);
5. an entity store that `validateEntities` rejects fails closed (`nonconformingEntities`);
6. when a rule whose scope holds at the request has a temporal leaf that reads an attribute of a scope entity the event does not supply, the decision fails closed (`missingScopeEntity`);
7. when an information-provider invocation of the policy set fails on the decision event, the decision fails closed (`providerError`). Every invocation in a policy set is evaluated for every decision event (guide chapter 5, "The provider contract"), so a failure fails the decision whichever rule the invocation belongs to;
8. when a provider's output is not a value of its declared type, the decision fails closed (`nonconformingProviderOutput`);
9. otherwise the event's Cedar request is decided by the per-request authorizer. Each temporal leaf is valued by whether it holds at `n`, after pin injection and under the schema's visibility. Each provider leaf is valued by its output under the providers `ω`;
10. under a reading that reports an error for some out-of-range results, the response is the one every completion of the reading gives; when two completions respond differently, the decision fails closed (`temporalError`).

`PolicySet.Admits` bundles the checks of steps 1 to 8. Each failing check has its theorem (`authorize_no_principal`, `authorize_nonconformingEvent`, `authorize_nonconformingContext`, `authorize_nonconformingEntities`, `authorize_missingScopeEntity`, `authorize_providerError`, `authorize_nonconformingProviderOutput`), and a decision that passes them is decided by the response or fails for a temporal error (`authorize_of_admits`). A failed-closed decision denies.

#### Scope entities a leaf reads

A temporal leaf reads the principal's and the resource's attributes off the entity data supplied with the decision event (`Event.entityAttr?`). Cedar treats an attribute read of an entity its store does not hold as a runtime error (`entityDoesNotExist`) of the policy that reads it, and skips that policy. On the temporal side, such a read is a term that does not resolve, so a comparison with it is false and its negation true: `!(principal.level < 3)` holds of a principal with no data, which fails open. The specification fails the decision closed instead (`FailClosed.missingScopeEntity`), when:

- a rule whose scope holds at the request (Cedar evaluates its principal, action, and resource constraints to `true`; `Policy.ScopeHolds`, decided by `Policy.scopeHolds`),
- has a temporal leaf that, after pin injection, reads an attribute of the principal or the resource (`Formula.scopeReads`: a `principal.<path>` or `resource.<path>` term in a comparison operand, a predicate argument, a pin, or an aggregation body, whose path is not empty),
- and the event's entity data does not hold that entity (`Event.supplies`).

The rule is the smaller of the two that make soundness at the request hold without a hypothesis on the entity data (`decision_sound`). The other would fail the decision closed for every leaf that reads an absent entity, whatever its rule. A rule whose scope does not hold is neither satisfied nor erroring, whatever its leaves (`isAuthorized_congr_scope`), so its leaves cannot change the response, and failing closed for them would let a rule that does not apply to a request deny it: a policy set with one rule over `OAuthUser` principals that reads `principal.level` and another over service principals would deny every service request whose event supplies no entity data. The rule is static: it depends on the rule's scope, the leaf's syntax, and the supplied data, not on what an evaluation of the leaf reaches. Satisfaction is a relation, with no evaluation order, so "what an evaluation reads" would depend on an implementation's strategy, and on the trace. The rule does not look at the facts of the leaf's position either: a leaf guarded by `principal has level` fails the decision closed when the principal is absent, though Cedar's `has` would be false there. That errs on the closed side, and keeps the check to the rule's scope and the leaf's syntax. A decision whose rules read no scope attribute, which includes every Cedar policy set, is unaffected (`scopeEntitiesSupplied_of_scopeReads_nil`).

The decision is defined for every trace. The language's decisions are made over traces of conforming events whose timestamps strictly increase, because an authorizer stamps every event it accepts after the last and rejects a nonconforming one (see [Ingestion](#ingestion-stamping-and-conformance)). A decision event is nonetheless checked again at step 3, so that `authorize` fails closed on such an event in every trace, not only in the traces ingestion builds.

#### Failing providers

The meaning of the providers is `ω : Provider.ResolvedCall → Provider.Output`: each resolved invocation, after its output-method chain, produces a value or fails. The crate fails an invocation when its Rhai script throws, when a caller-supplied `ProviderResolver` returns an error, when a method of its output chain fails, and when the provider is undeclared and no resolver supplies its value. Any such failure denies the whole decision before Cedar runs, with the error in the response's diagnostics (`api.rs`, `decide_at` and `eval_provider`); the specification's `FailClosed.providerError` is that denial.

An output that does not have its declared type, such as an id outside a declared enum or a record with an undeclared attribute, is a broken provider contract too. The specification fails the decision closed for it (`FailClosed.nonconformingProviderOutput`), and the crate denies it too. The crate checks each output as it coerces it to its declared type, inside the invocation (`extension/provider/eval.rs`, `coerce_to_declared`), and checks every output again after every provider has run (`conformance.rs`, `provider_output_nonconformance`).

The guide calls an erroring script or resolver undefined behavior, and the reference interpreter's denial its implementation choice, while an output outside its declared enum must deny on every implementation (guide chapter 10, "Fail closed at runtime"). The specification fixes the reference's choice for both: an implementation that plugs into the crate's `Authorizer` as a temporal engine decides through the same frontend, and so makes the same choice. A provider failure could instead be made a Cedar evaluation error of the policy that contains the leaf, which Cedar's authorizer would report among the erroring policies. The crate does not do that, and it would let a `forbid` whose provider fails stop applying, so that the request could be allowed.

### Readings of out-of-range results

The language leaves implementation-defined what a comparison sees when an aggregate's exact total, or the exact result of an arithmetic operation, lies outside the `Long` range (guide chapter 8, §5.4). `ImplChoices` holds both choices. `ImplChoices.widen` computes exactly, `ImplChoices.clamp` clamps to the range (the reference implementation's choice, which its saturating `i64` arithmetic computes operation by operation), and `ImplChoices.error` reports an error (`Dogwood.Spec.Temporal.Readings`):

- **Admissible readings.** A reading is admissible when it preserves the side of the range an out-of-range result lies on, or reports an error (`ImplChoices.Admissible`). Widening, clamping, and reporting errors are admissible (`widen_admissible`, `clamp_admissible`, `error_admissible`); wrapping around, as two's-complement arithmetic does, is not. Two admissible total readings agree on a comparison of an aggregate with a threshold strictly inside the range, when every result the aggregate's body computes is in range (`sat_interior_threshold`).
- **Erroring readings fail closed.** A reading that reports an error for some results is *completed* by every total admissible reading that agrees with it elsewhere (`ImplChoices.Completes`); every reading has a completion (`exists_completes`). The response under the reading is the response every completion gives, when they all give the same one; otherwise the decision depends on how an erroring result would have been read, and it fails closed (`ImplChoices.supervaluate`, `PolicySet.respond`, `FailClosed.temporalError`). So the outcome fails closed for a temporal error, or is the outcome of every completion (`authorize_dichotomy`). The erroring reading allows only what every total admissible reading allows (`authorize_error_allow`).
- **The total semantics is unchanged.** A total reading is its own only completion (`supervaluate_total`), so under widening or clamping the decision is `Sat`'s (`respond_total`, `authorize_decided`).
- **In range, the readings agree.** When every result a condition computes is in range (`Formula.InRange`), every reading gives it the same truth value (`sat_readings_agree`), and every reading decides alike (`authorize_readings_agree`).

### Soundness

`Dogwood.Thm.soundness` states, for a valid policy set, at a decision every check of which passes, over a trace whose events conform:

1. **readings**: under every reading, the outcome fails closed for a temporal error, or it is the outcome under every completion of the reading, and every completion is total;
2. **the Cedar part**: under every reading, every lowered rule evaluates, on the augmented request and the decision's entity store, to a `Bool` or one of the runtime errors validation cannot rule out (Cedar's `typecheck_policy_with_environments_is_sound`); so does every rule under Dogwood's evaluator; and the response is Cedar's on the lowered rules (`cedar_sound`);
3. **the temporal part**: under every total reading, every temporal leaf, in every environment its rule admits of which the decision event is an instance, when the event supplies the scope entities the leaf reads, at a position whose facts hold, is sound after pin injection (`leaves_sound`, `Formula.WellTyped.sound`): every comparison its satisfaction reaches has operands that denote values, every `exists` witness and every aggregation row it uses is typed, and every aggregate it reaches has a total.

The corollaries:

- **`!=` and `!(==)` coincide** wherever both operands denote (`sat_ne_iff_not_eq`), which soundness guarantees for every comparison of a valid leaf.
- **The binding idiom is substitution**: `exists x. (t == x && φ)` holds exactly when `φ` holds with `x` bound to the value `t` denotes, when `t` does not mention `x` (`sat_binding_idiom`); under clamping every operand that denotes is such a value (`clamp_denotes_value`).
- **Out-of-range results**: under every reading, the decision fails closed for a temporal error or is the decision of every completion of the reading (`authorize_dichotomy`), so under the reading that reports errors it fails closed or agrees with every admissible total reading (`authorize_error`); when every result is in range, every reading gives the same decision (`authorize_readings_agree`).
- **A leaf matters only where its rule's scope and its facts hold**: two leaf valuations that agree, on every rule whose scope holds at the request (`Policy.ScopeHolds`), on every leaf whose facts hold there, give the same response (`isAuthorized_congr_scope`, and `isAuthorized_congr_facts` without the scopes).
- **Soundness at the request**: under a total reading, every temporal leaf the response depends on is sound in the request's environment (`decision_sound`). The temporal part's hypotheses follow from the decision's checks: a rule whose scope holds admits the request's environment (`admits_of_scopeHolds`), a fact Cedar's `has` test establishes holds of the event's data (`holds_of_holdsIn`), the decision event is an instance of the environment (`instanceOf_of_admits`), and it supplies, with conforming attributes, the scope entities the leaf reads (`supplied_of_admits`, `supplies_of_admits`).
- **No allow is caused by an unresolved or ill-typed value**: an allow of a valid policy set, over a trace whose events conform, is the allow of every completion of the reading, at a decision every check of which passes; under each completion every rule evaluates to a `Bool` or a runtime error, and every temporal leaf the response depends on is sound, so no comparison it reaches has an operand that does not resolve (`allow_sound_leaves`, and `allow_sound` for the Cedar part alone).
- **Nonconforming and missing data fail closed**, each kind with its own reason (the `authorize_*` theorems listed in [Decisions over traces](#decisions-over-traces)).

### An executable evaluator

`Dogwood.Eval` turns safety into a decision procedure. `eval ι rate σ e vis J v j φ` decides whether `φ` holds at timepoint `j`. The temporal operators search the finitely many earlier timepoints. Where `Sat` quantifies over all values, `eval` searches the candidates of `Dogwood.Eval.Candidates`:

- an `exists` whose body binds its variable by an equality `x == t` among its top-level conjuncts, possibly under nested `exists` of other variables, with `t` mentioning none of them, tries only the value `t` denotes (`bindingValue?`). Any witness must be that value. Without this shortcut, an `exists` bound to a `sum` would try every integer between minus and plus the sum of the candidate rows' summand magnitudes;
- any other `exists` tries each candidate value of its variable;
- an aggregate's rows are the rows of candidate values that satisfy its body.

A candidate is a value the condition's predicates read off the trace up to `J`, a timepoint up to `J`, or a value a binding equality's other side can denote: a ground operand, a value its aggregate can compare as, or a compound evaluated on candidate operands. Because restriction is a closure, the candidates of a `&&` chain are computed by iteration, one round more than the chain has free variables (`Formula.cand`).

`Dogwood.Thm.rr_sound` proves the candidates sound: in a safe condition, a restricted variable holds a candidate in every satisfying assignment. So every aggregate has a total (`total_exists`), an `exists` holds exactly when a candidate witnesses it (`sat_exist_iff`), and `eval` decides `Sat` on every safe condition (`eval_iff`). `Eval.authorize` and `Eval.replay` follow `PolicySet.authorize`, with each leaf decided by `eval` and every conformance check computed; `authorize_eq` and `replay_eq` prove them equal to the specification under a total reading, for a policy set whose leaves are safe.

The search is exhaustive, so the cost of an aggregate is exponential in the number of variables its domain binds. The evaluator is meant for comparing the specification with the crate's verdicts, not for enforcement.

### What is left abstract

- **Information providers.** The meaning of the providers, `ω` (see [Failing providers](#failing-providers)), is a parameter. The guide's provider contract requires a provider to be pure, which `ω` reflects by being a function. Any argument may be absent on an event, which `Provider.ArgValue.absent` reflects. `Provider.total f` is the meaning of providers that never fail.
- **The reading of out-of-range results.** A parameter, `ι : ImplChoices`; see [Readings of out-of-range results](#readings-of-out-of-range-results).

### Ingestion: stamping and conformance

An authorizer assigns the timestamp of every event it accepts (`Dogwood.Spec.Ingest`). A submission carries no timestamp. It carries the event, and arrives with a **clock reading** (`Arrival.event e clock`): the authorizer's clock when the event arrived, in ticks of its rate. When a recorded trace is replayed, the reading is the recorded time in ticks, `seconds × rate.perSecond` (`Trace.readings`).

`Log.submit` **stamps** an accepted event with its reading, or with one tick after the last event's stamp when the reading is not later (`stampAfter`): `max(reading, last + 1)`. The stamp is at least the reading (`stampAfter_ge`) and after the last stamp (`lt_stampAfter`), so every log that ingestion builds keeps the language's timestamp rule, `Trace.StrictlyIncreasing`, by construction (`ingest_strictlyIncreasing`), and no event is rejected for its time. On readings that already strictly increase, every event is stamped with its reading (`stamp_of_strictlyIncreasing`). An implementation may stamp other records, such as its deployments, from the same sequence, which the event-log contract admits (`Arrival.Stamps`).

**Stamps per key under partitioned evaluation.** Under partitioned evaluation each key's log is stamped on its own (see [Key-local semantics](#key-local-semantics-is-a-visibility-predicate)). The stamps of a key's log are that key's events' stamps in the single log when the readings strictly increase across all keys (`stamp_partitionLog_of_strictlyIncreasing`), and can be earlier otherwise, since the single log stamps each event after the previous event, whatever its key. `eq_stamp_iff` states pointwise what it is for a trace to be the stamping of a log of readings, so a proof of an implementation can show that the log it keeps is `Trace.stamp` of its readings.

**A submitter cannot choose a timestamp.** The reading is the authorizer's own clock. If the timestamp came from the submission, and one that was not after the last were rejected, a submitter could push the clock forward: an event stamped far in the future would make every later event not stamped later still, an administrator's revocation included, stale and rejected, and the submitter's own later requests, stamped further ahead, would leave its earlier history outside every window, so that its rate limits reset. Stamping closes the attack. It also never refuses a fact that already happened: an event that arrives within the same tick as the last, or after the clock stepped back, is stamped one tick later and enters the log.

**Readings far from the last stamp.** A reading at or behind the last stamp gets one tick more than the last stamp. A reading far ahead of it is the stamp, and the stamps then run ahead of the clock: each later reading behind them gets one tick more than the last, until the clock catches up. The specification bounds neither. An implementation may bound the second: it may refuse a submission when its last stamp is too far ahead of its clock, rather than issue future-dated stamps, and when its stamps reach the end of their range. The event-log contract admits both refusals as `Rejection.unavailable`.

**Nonconforming events.** `Log.submit` rejects an event that does not conform to the event schema (`Rejection.nonconforming`, `Arrival.nonconformance?`): of no declared signature, with a logged record that is not an instance of its signature, or with a logged caller or symmetrically pinned field that contradicts its own request or that it logs without carrying the request-side value (the strict mirror rule, see [Runtime conformance](#runtime-conformance)). A rejected event does not enter the log, so no decision ever sees it. The rejection is reported to the event's submitter (`Reply.rejected`); it is never silent, and it is not a decision, in particular not a `Deny`. A deployment is never rejected. Every log that ingestion builds holds conforming events only (`conforming_ingest`). Ingesting a trace's events, each with its timestamp as its reading, builds its conforming events, stamped (`ingest_events`: `Trace.stamp` of `Trace.conforming`; `ingest_readings` for a recorded trace in seconds). On a trace of conforming events whose timestamps already strictly increase, ingestion accepts every event at its own timestamp, and replies with `PolicySet.authorize`'s outcome at its timepoint (`ingest_of_strictlyIncreasing`).

The theorems that need the timestamp rule state it as a hypothesis, or the weaker `Trace.Nondecreasing` when that suffices, as the horizon theorem does; ingestion discharges it.

The reference interpreter takes the caller's timestamp, in seconds, and neither checks nor enforces the rule (see [Relationship to the reference implementation](#relationship-to-the-reference-implementation)).

### Policy updates

An authorizer's rules can change while events flow. The specification states such changes in the semantics (`Dogwood.Spec.Log`). An authorizer's history is a log (`Log`) whose entries are the accepted events and the deployments (`Entry`), in one order. A deployment names the rules in force from it on. The events of the log are its trace (`Log.trace`); a deployment takes no timepoint. An authorizer built with a policy set `P` starts with the rules of `P` in force. `Log.decide reading ι P ω log i` is the outcome of the entry at log position `i`: an event is decided against the rules in force before it, and a deployment decides nothing. For a log of events alone it is `PolicySet.authorize` (`decide_events`), and later entries never change it (`decide_append`).

**What a rule installed mid-trace sees.** An implementation may give either, and `UpdateReading` parameterizes the specification over the two readings:

- **retrospective**: a rule observes the whole trace, including the events accepted before its deployment. The reference interpreter has this reading: `Authorizer::update_policies` re-prepares its temporal engine with the new rules, and the built-in `InMemoryTemporalEngine` evaluates every leaf over the whole retained history, which is the whole trace (`authorize/mod.rs`, `engine.rs`).
- **prospective**: a rule observes only the events from the start of its monitor instance on. An implementation in which a newly added rule starts with an empty history has this reading, and so does one that keeps no event payloads and writes a leaf's state only from its installation on.

Under the retrospective reading, a decision is `PolicySet.authorize` with the rules in force, over the whole trace (`decide_retrospective`). Under the prospective reading, each rule observes the trace from its start (`PolicySet.LeafHoldsFrom`, `PolicySet.authorizeDeployed`), and two rules can give the same leaf different values (`isAuthorizedEach`). Observing from timepoint `s` is evaluating over the trace's suffix from `s`, as an empty monitor installed at `s` would (`leafHoldsFrom_iff_drop`). Timepoint indices stay global under both readings. An implementation may number a new monitor's timepoints from its installation instead; only equality observes an index, so the verdicts are the same.

**What identity a rule keeps.** A deployment names the monitor instance of each rule it puts in force (`DeployedRule.monitor`). A rule whose instance was in force just before keeps the instance's start (`startOf_kept`); any other rule starts at the next event (`startOf_new`), and so does a rule whose instance left the set and comes back. An instance names one rule: `Log.InstancesStable` requires every rule in force under one instance to be the same rule, so that a changed rule never reads state kept for the old one. An implementation that gives an updated or reset rule a new monitor, and never reuses a monitor's id, meets it. An implementation that keeps a leaf's state under an id that survives a change of its rule does not, unless the id changes with the rule, as when it includes a hash of the compiled rule. It also means that a rule removed and later installed again must not read the state its earlier instance left behind.

**Ordering.** A deployment is an entry of the one log, ordered with the events: every event before it is decided under the previous rules, and every event after it under the new ones. An implementation that records an update in the same log as the events, under the same lock, keeps this order. The event schema and the action schema are fixed for a log. The crate does not check this: `Authorizer::update_policies` accepts a policy set with another event schema or action schema, and checks only that it partitions temporal history the same way.

### The event-log contract

The semantics decides over one totally ordered log. An implementation that runs several instances, or that retries a step after a conflict, must still decide as if it had built one such log. `Dogwood.Spec.Contract` states the contract every run of an implementation must meet, `Run.Meets`. A run records the submissions an implementation received (each with an identity of its own, an arrival that carries a clock reading and no timestamp, and the event id its submitter gave the event, if any), the log it built (each accepted submission with the entry it became, `Logged`), the reply each submitter got, and the prefix of the log each deciding instance had observed. The contract is parameterized by a retry window `W`, in ticks; its default is five minutes (`defaultRetryWindow`). It requires:

- each submission is accepted at exactly one position of the log and told that position; or it is a retry of an accepted submission, absent from the log, and told that submission's position; or it is rejected, absent from the log, and told why (`Rejection.unavailable` covers a submission the implementation could not place, such as one that lost a serialization conflict, or one refused because the implementation's clock is too far behind its last stamp);
- no submission is lost silently, and none is accepted twice;
- every instance observes the same order: what an instance had observed when it decided an entry is a prefix of the log that contains the entry;
- an accepted event's outcome is `Log.decide` at its position, and so is the answer to a retry of it, over a prefix of the log its answering instance had observed that contains the position (`Run.Meets.retried`);
- no two entries of the log have the same retry key (`Run.Meets.keyed`), and a rejection as a duplicate is truthful (`Run.Meets.duplicate`);
- each logged entry stamps its submission after the log before it (`Run.Meets.stamped`, `Arrival.Stamps`): an event's stamp is at least its clock reading and after the previous event's stamp, and a deployment is the submitted one. Ingestion's `max(reading, last + 1)` is the least such stamp (`stampAfter_le_of_stamps`). The contract admits a later one because an implementation may stamp its deployments from the same sequence as its events, so an event that follows a deployment within a tick of it is stamped one tick after the deployment's stamp;
- every event of the log conforms to the event schema (`Log.Conforming`), and a rejection for nonconformance is truthful.

A submission is a **retry** of an accepted submission (`Submission.RetryOf`) when it has the same retry key (`Submission.retryKey?`: the partition key of its event, so the same log of an implementation that keeps one log per key, its event id, and its action and kind), it is the same event (the same logged record and the same request: principal, resource, context, and entity data), and its clock reading is at most `W` after the accepted submission's stamp. A retry is not ingested again, and is answered at the accepted submission's position, with the decision there. A submission with the retry key of an accepted one that is not a retry of it, because its content differs or it comes after the window, is rejected (`Run.Meets` does not fix the reason, and a single instance gives `Rejection.duplicate`): it is not ingested, and not decided. A submission without an event id has no retry key, so it is never a retry, nor a duplicate.

The theorems make it usable: an accepted outcome is the decision over the whole log, whatever prefix its instance had observed (`Run.Meets.outcome_eq`, by `decide_append`); a submission has at most one position (`Run.Meets.position_unique`); nothing is lost (`Run.Meets.logged_retried_or_rejected`); a logged event is its submission's event, stamped at or after its reading and after the event before it (`Run.Meets.logged_event`); the decisions are made over a trace that keeps the rule (`Run.Meets.trace_strictlyIncreasing`, from the stamping clause by `wellFormed_of_stamped`). The contract does not relate readings to real time, since a reading is what the implementation's clock said. A single instance that answers a retry at its original's position, rejects a duplicate, and ingests every other submission in arrival order with `Log.submit` meets the contract, for every window (`sequential_meets`), so the contract is consistent.

On retries: a retry, and a duplicate, is not in the log (`Run.Meets.not_logged_of_sameKey`, `Run.Meets.retry_not_logged`), and a single instance's log is the same after a retry as before it (`sequential_retry_log`); the answer to a retry is its original's, accepted at the original's position with the decision there, or the retry is rejected as unavailable, never as a duplicate or as nonconforming (`Run.Meets.retry_reply`, `Run.Meets.retry_accepted`), and a single instance answers it as it answered the original (`sequential_retry_reply`). The decision at a position depends only on the log up to it, so the answer does not change when a deployment comes between the original and its retry. A duplicate is rejected (`Run.Meets.duplicate_rejected`). When no two submissions share a retry key (`Run.FreshIds`), the contract is the contract without retries (`Run.MeetsWithoutRetries`, the contract without event ids) with no rejection as a duplicate, whatever the window (`Run.meets_iff_withoutRetries`, and at the window `0`, `Run.meets_zero_iff_withoutRetries`).

The contract describes an authorizer with one log. It does not cover one that keeps a separate trace per partition key, as the crate does under `AuthorizerBuilder::partition_temporal()`. The specification defines the evaluation such an authorizer computes (`Dogwood.Spec.Partitioned`), but no contract for it.

### Lemmas for proofs of implementations

These are general facts about the specification that a proof of an implementation can use.

- **Decisions with an implementation's leaves** (`Dogwood.Thm.Implementation`): `PolicySet.authorizeWith` is the decision with the temporal leaf values supplied, and `authorizeWith_eq` shows it is `PolicySet.authorize` under a total reading when they decide `PolicySet.LeafHolds` at the admitted decision events. `leafHolds_iff_global` reads a leaf under global visibility when the schema has no universal symmetric pin. `decideWith_congr` and the `decideWith_*` lemmas (`Dogwood.Thm.Decision`) cover any decision built on the skeleton.
- **Subsequences and renumbering** (`Dogwood.Thm.Slice`, `Dogwood.Thm.Renumber`): `Sat` over a subsequence of the trace is `Sat` over the trace with the subsequence's timepoints visible, with the valuation's timepoints renumbered (`sat_subseq`, for every condition); for a valuation without timepoints no renumbering is needed (`sat_subseq_noTp`, `sat_slice`). The events of a prefix that satisfy a predicate form such a subsequence (`subTrace_filter`), and so does a suffix (`subsequence_drop`).
- **Partitions** (`Dogwood.Thm.Partition`): an event is *mine* exactly when its partition key is the decision event's (`mine_iff`); on an `EventSchema.Partitionable` trace the visible timepoints are those of the decision's partition (`visible_iff_partitionKey`), and a leaf holds exactly when it holds at the last timepoint of the partition read as a trace of its own (`leafHolds_iff_partition`). Every log ingestion builds is `Partitionable` (`Dogwood.Thm.Mirror`, see [Runtime conformance](#runtime-conformance)).
- **Partitioned evaluation** (`Dogwood.Thm.Partitioned`): the unfolding of `PolicySet.PartLeafHolds` over the decision's partition log (`partLeafHolds_iff`) and over the key's whole log, at the decision's position in it (`partLeafHolds_iff_keyLog`); values are past-only (`partLeafHolds_append`); over a partition whose readings strictly increase, stamping changes nothing (`partLeafHolds_iff_of_strictlyIncreasing`); stamping a prefix, an extension, and a filter of strictly increasing readings (`stamp_take`, `stamp_append`, `stamp_filter_of_strictlyIncreasing`), and what stamping is, pointwise (`eq_stamp_iff`). `authorizePart_of_admits` reads the partitioned decision at an admitted event.
- **Horizons** (`Dogwood.Thm.Horizon`): see below.
- **Restriction** (`Dogwood.Thm.Restriction`): the closure is monotone (`Formula.restricts_mono`), depends only on the restricted variables a condition reads (`Formula.restricts_congr`), and is reached in finitely many rounds (`Formula.exists_closed_stage`); a chain's closure splits over its conjuncts (`Formula.restricts_and_iff`). An evaluation that orders a chain's conjuncts can rely on these.
- **Values** (`Dogwood.Thm.Values`, `Dogwood.Thm.Valuation`): clamping (`clampLong_idem`, `clamp_arithValue`, `clamp_aggregateValue`), comparison operands (`ofValue_inj`, `ofValue_eq_num`, `ofValue_cases`), and reading an aggregation row back off a valuation (`bindAll_map`, `map_bindAll`, `lookup_zip_map`).
- **Traces and windows** (`Dogwood.Thm.Trace`, `Dogwood.Thm.Horizon`): the timestamp rule at indices and under sublists, prefixes, suffixes, and appends; `Formula.WellTyped.windowsNonneg`, since typing makes every window positive; pin injection keeps windows, horizons, and the absence of `tp`; `Window.ticks_seconds` and `Window.reach_of_nonneg` read a window in ticks.
- **Rates** (`Dogwood.Thm.Scale`): `sat_scale`, `denotes_scale`, `total_scale`, `leafHolds_scale`, and `authorize_scale` move a proof from one rate to a multiple of it; `decideWith_congr_event` compares two decisions whose timepoints carry the same event.
- **Invariances** (`Dogwood.Thm.Invariance`): a proof can shift every timestamp or clock reading, rename variables, and ignore policy ids (the Invariances row of [Theorems](#theorems) lists the lemmas).

#### Horizons

`Formula.horizon rate` is how far back, in ticks of the rate `rate`, a condition can look from the timepoint it is evaluated at: a temporal operator adds its window to the horizon of what it scans, and `&&`, a comparison, a compound operand, and the two sides of `since` take the larger horizon of their parts. An aggregate looks as far back as its `where` body. A negative window counts as `0` (`Window.reach`); typing rejects one anyway. `PolicySet.horizon` is the longest horizon of a policy set's temporal leaves, at its rate.

`sat_horizon`: on traces whose timestamps never decrease, whether a condition holds at timepoint `j` depends only on the timepoints `k ≤ j` with `ts(j) − ts(k) ≤ horizon`, aggregates included. Two traces that agree on those timepoints in either trace, with their visibilities, give the same verdict. The rule's strict increase implies the hypothesis; without it, `previous` and `since` can read a timepoint between their match and `j` whose timestamp lies outside the window. `sat_drop_horizon` turns it into pruning: dropping a prefix of the trace that lies beyond the horizon changes nothing, for a valuation without timepoints. `authorize_horizon` and `authorize_drop_horizon` lift both to decisions: a decision depends only on the events within the policy set's horizon of it, and an implementation that keeps only those events decides as the specification does.

## Conformance against the crate

`bridge/` is a Rust program built on the `dogwood-language` crate in this repository, through a path dependency. It handles the frontend work this specification does not: it parses, expands, derives, lowers and validates a bundle with the crate, then exports the result as JSON: the typed event signatures, the action schema (in Cedar's validator form, without the context attributes lowering hoisted), the provider declarations, the rules, every finding of the crate's validator, and the crate's verdict at each event. The Lake project's `conformance` executable reads the JSON and compares it with the specification. `conformance/run.sh` exports the guide's examples, the crate's test corpora (the temporal, mixed, macro, expected-failure, arithmetic (`experimental`), and provider corpora), and the probe bundles.

```bash
LEAN_CC=/path/to/cc dogwood-lean/conformance/run.sh
```

- **Validation, by category.** For every bundle that lowers, the specification's `PolicySet.validationFindings` and the crate's validator must report a finding of each category together, or not at all.
- **Decisions.** For every lowered bundle whose traces the bridge exports (the checker reports the others as not replayed), each trace is replayed twice, once with the crate's `Authorizer` and once with `Dogwood.Eval.authorize` under clamping, and the verdicts must agree at every event. Where the specification fails a decision closed on nonconforming or missing data the crate decided on, the checker reports a runtime gap of that kind and compares the verdict on conforming data instead, so that the comparison of the temporal semantics is kept.
- **Ingestion.** Each recorded trace is replayed as its authorizer would build it: each recorded time, in seconds, is its event's clock reading in nanoseconds, and each event is stamped (`ingest_readings`). Events that ingestion rejects as nonconforming are reported, and the conforming events are replayed alone. A trace whose recorded times do not strictly increase is reported apart, since the crate takes the times as given.

The crate and the specification disagree in known ways, and `conformance/baseline.txt` lists every disagreement the run expects; the run fails only on a disagreement the baseline does not list. The verdicts the baseline lists differ on probes of the time model (`decreasing_timestamp_read`: the specification stamps a `Read` recorded before a login after it; the crate takes the time as given), and on decisions whose rules read an attribute of a scope entity the event does not supply, which the crate decides over a bare entity. The crate's validator enforces the specification's validity rules, apart from the validation findings the baseline lists and an action schema fed forward from a lowering with provider leaves, which the crate accepts and `namesFresh` rejects, and its authorizer makes the specification's runtime checks, and fails closed where it does, apart from that scope-entity gap. `Dogwood.Thm.authorize_eq` makes the decision comparison a comparison with the specification itself, not just with another implementation. [`conformance/README.md`](conformance/README.md) describes the method, its limits, the results by category, and the gaps between the two validators and runtimes.

## Scope

The specification's abstract syntax is the output of the crate's frontend. That output has had the following done to it:

- the source has been parsed, the macro library merged, and macros expanded;
- surface operators (`!=`, `>`, `>=`, extension methods) have been desugared into Cedar's abstract syntax, as Cedar's own parser does;
- each temporal comparison operand has been parsed into a tree of compound operands: left-associative, with `*` binding tighter than `+` and `-`, and an operand without an operator collapsed to its single term;
- `guardrails { E }` has been read as `when { E }`, and provider invocations have been recognized;
- the event-schema DSL has been derived against the action schema, producing typed event signatures, decision flags, and pins;
- the action schema has been read into Cedar's validator form, with the enum entity types the provider declarations inject.

The specification does not cover these steps. `Dogwood.Frontend` ports the steps after the parsers, as an implementation to compare with the crate, not as a statement of what they must compute. The specification specifies validation, lowering, and the decision, and gives meaning to every syntactically valid policy set, including ones validation rejects; its theorems say what validation guarantees.

Of the control plane, the specification covers what a deployment means for the decisions that follow it ([Policy updates](#policy-updates)). It does not cover how a control plane checks a change before it deploys it, how it assigns monitor instances to the rules of a change, or a change to the event schema, the action schema, or the providers' declarations.

## Relationship to the reference implementation

The guide's formal chapter treats the crate's code as authoritative, and this specification follows the crate except where noted. Most of the differences below concern representation: the reference implementation carries event data as JSON-like values and Cedar entities as strings, while this specification uses Cedar's values throughout. The others are places where the specification holds the reference to a rule the reference does not enforce; `conformance/README.md` ("Validator and runtime gaps") lists those the conformance run shows, with their bundles.

- **Values.** Event fields, request contexts, and entity attributes are Cedar values here. The reference interpreter's value type has a `Null`, ordered arrays, and decimal text that Cedar may reject. Cedar values have none of these. Arrays become Cedar sets. Decimals compare by Cedar's numeric value in both. Temporal array constants are rejected by lowering, so no temporal term denotes an array.
- **`ip`, `datetime`, and `duration` values.** The reference implementation carries these as raw `__extn` records, a gap its source documents (`api.rs`, `cedar_escape_to_value`). Here they are Cedar extension values.
- **Arithmetic on time.** Timestamps and windows are mathematical integers. The reference implementation saturates `i64` arithmetic, which differs only for timestamps or windows near `2^63` seconds.
- **The unit of time.** The reference interpreter counts timestamps and compares windows in seconds; the specification counts ticks of a declared rate, nanoseconds by default. Over a trace recorded in seconds, the two decide alike: the specification at nanoseconds over the trace scaled by `10⁹` decides as at one tick per second over the trace itself (`authorize_scale`), which is the reference's unit.
- **Aggregate totals and arithmetic results.** The reference implementation clamps out-of-range totals, and saturates each arithmetic operation in tree order (`ImplChoices.clamp`), one of the readings the specification admits (see [Readings of out-of-range results](#readings-of-out-of-range-results)).
- **Validation.** Validity is more permissive than the crate's validator in the three ways [Valid policy sets](#valid-policy-sets) lists. The baseline lists two more findings that the crate's validator reports and the specification does not. One is a cascading Cedar finding for an undeclared provider or method. The other is for a Cedar part that reads the context attribute a leaf is hoisted to, which the bridge shows the specification as the leaf itself (`validation_context_read_own_leaf_name`).
- **Request and event conformance.** The reference implementation checks requests, logged records, entity stores, and provider outputs as the specification does, in the order of `PolicySet.decideWith`, and ingests no nonconforming event. `Authorizer::submit` rejects a nonconforming history event (`Rejection::Nonconforming`) and answers a nonconforming decision event with a fail-closed `Deny`, where the specification's `Log.submit` rejects both. The crate's mirror check (`conformance.rs`) is the specification's strict rule by default (`MirrorRule::Strict`); `AuthorizerBuilder::mirror_rule` selects a weaker rule, under which the crate ingests a scope-less event that logs a caller, which the specification rejects.
- **External declarations (Cedar 4.14).** The crate's authorizer builds the entity store with Cedar's `Entities::from_entities` against the schema, which rejects an entity whose own type is declared `external`, and it leaves external actions out of the schema's action entities. The specification's entity store holds an external action as Cedar's validation view of it, and its `validateEntities` accepts an entity of an external type without attributes or tags. Both can matter only for a policy set without rules, the only valid one against an incomplete schema (`Valid.complete`): there the crate fails closed a decision whose store holds an entity of an external type, and the specification denies it. Both deny.
- **Scope entities.** The reference adds a bare entity for the request's principal and resource when the event supplies none, without validating it. So a temporal leaf that reads an attribute of a principal the event does not supply reads a value that does not resolve: a comparison with it is false, and its negation true. The specification's entity store is the schema's action entities and the supplied data only, and it fails such a decision closed (`FailClosed.missingScopeEntity`, see [Scope entities a leaf reads](#scope-entities-a-leaf-reads)).
- **Caller-stamped timestamps, in seconds.** The specification's authorizer stamps every event it accepts, in ticks of its clock, after the last (see [Ingestion](#ingestion-stamping-and-conformance)). The reference implementation takes the caller's timestamp, in seconds, as given: an `Event` carries its timestamp, `InMemoryTemporalEngine::observe` appends every event to the trace (`engine.rs`), and `parse_trace` keeps the file's order and times. It neither checks nor enforces the timestamp rule. The guide says so ("The interpreter preserves supplied timestamps; it neither constructs nor validates that sequence", chapter 4), and only the crate's test corpora are guarded, by `tests/trace_monotonicity.rs`. On a trace whose times strictly increase, stamping changes no time, so the two decide alike. On a trace whose times do not, the crate decides over times the specification's authorizer would not assign. An event at the time of the one before lies inside every window of a later event, as its stamp one tick later does. An event recorded before the one before it sees every earlier event with a later time drop out of its windows; `formerly` and the anchor scan of `since` keep looking past it, while, without a pin, `previous` fails when the event just before has a later time. The specification stamps it one tick after the last, inside those windows. The conformance run's probes show both cases (`equal_timestamp_read`, `equal_timestamp_logout_read`, and `decreasing_timestamp_read`, whose verdicts differ).
- **Key-local semantics with out-of-order timestamps.** Under a universal symmetric pin, the reference implementation evaluates rewritten leaves (`event_schema/relativize.rs`) whose `previous` and positive-left `since` consider only the key's events *inside the window*. The specification follows the guide's slice reading: `previous` is the key's last event before the timepoint, and `since`'s left must hold at every key event after the anchor. The two agree whenever timestamps never decrease in arrival order, and so on every trace a stamping authorizer builds: `Dogwood.Thm.Frontend.relativization_correct` proves it of the Lean port of the rewrite (`Dogwood.Frontend.LeafPasses.relativize`), for timestamps that strictly increase on a trace whose length fits a `Long`, and its core, `rsat_relCond`, for timestamps that never decrease. They can disagree when an intervening event of the key carries a timestamp outside the window. For example, take `previous within 1h Login{…}` over alice's Login `@0`, Read `@100000`, Read `@60`. The guide, this specification, the reference without a pin, and the reference's partitioned mode all deny the last read; the reference's default mode allows it. A stamping authorizer would stamp the last read one tick after the read before it, and the guide, this specification, and both of the reference's modes would then all deny it.
- **Partitioned evaluation.** The reference's opt-in partitioned mode (`AuthorizerBuilder::partition_temporal`) stores and evaluates each key's events separately. It numbers timepoints per partition, which changes no verdict (`sat_subseq`), and files every event under its logged pin field rather than its request-side value; under event conformance the two are equal, for history events as for decision events (`mine_iff_mineReq_of_strict`), and every conforming trace suits partitioned evaluation (`partitionable_of_strict`). The specification defines partitioned evaluation too (`PolicySet.PartLeafHolds`, `PolicySet.authorizePart`), with each key's log stamped on its own. The crate does not stamp: on a stream whose timestamps strictly increase within each partition, stamping changes nothing, and the specification's value is the leaf's over the partition with the events' own timestamps (`partLeafHolds_iff_of_strictlyIncreasing`).
- **Action identity.** An event's action is a structured `EntityUID` here. The reference stores an action as a namespace path and an id. An event built with a bare id (`Event::builder("Login", …)`) has an empty namespace, so it never matches a predicate on `Action::"Login"`, even though Cedar renders it as `Action::"Login"`. The specification has one form of each action.
- **Leaf hoisting.** The reference implementation stores leaf values in `context.<id>` and `context.providers.<id>` attributes. Validity requires the specification's own attribute names to be fresh, so no request context can collide with them. The crate reserves its names likewise: its authorizer refuses a request context that supplies one, its validator rejects a rule that reads one (in the Cedar part or in a leaf), and its lowering refuses to replace a declared context attribute of a hoisted temporal leaf's name by the leaf's `Bool`.
- **Provider arguments.** Both read a provider argument's `principal` / `resource` off the request's scope. The reference implementation strips every leading `context` segment of a `context.<path>` argument, not just the first. When the path does not resolve, it falls back to a top-level lookup of the path's last segment in the request context (`api.rs`, `resolve_field_path`). The specification strips exactly the one `context` root, and has no fallback.
- **Fail-closed causes.** A malformed principal, action, or resource UID is a string-level failure that structured `EntityUID`s cannot express. A temporal-engine error has no counterpart in a total semantics, except a reading that reports errors. The specification's causes are the checks of [Decisions over traces](#decisions-over-traces).
- **Policy updates.** `Authorizer::update_policies` accepts a new event schema or action schema, which the specification keeps fixed for a log (see [Policy updates](#policy-updates)).
- **Responses.** A response is Cedar's `Response`: determining policies are rule ids (`policy_<i>` after lowering), and errors are the erroring rules' ids.
- **Pins and compound operands.** The specification injects pins into every predicate of a leaf, including the predicates of an aggregate that is a leaf of a compound operand, and so does the reference implementation: its pin injection (`event_schema/pin.rs`, `inject_into_operand`) and its relativization rewrite (`event_schema/relativize.rs`, `rewrite_term`) descend into `Term::Arith`. Three of the guide's examples (`cap_open_agent_prs_windowed`, `refund_budget_settled_plus_current`, `touchless_share_capped`) have such compound aggregates, and the conformance run checks that every predicate of their exported leaves carries its event's pins (`pinsCarried`).
- **Validation of aggregates in compound operands.** The crate's event-name check (`event_schema/validate.rs`, `validate_term`), its time-point-dependence check of aggregation bodies (`extension/temporal/validate.rs`, `is_tp_dep`), and lowering's array-constant rejection (`api.rs`, `term_has_array`) descend into compound operands, as the specification's typing and `Formula.MonitorsTime` do, so a misspelled event (`Refnd::response{}`) or a body that monitors nothing is rejected when written `(count …) + 0` too; the probes `validation_compound_aggregate_event` and `validation_compound_aggregate_constant` show it.
- **Conditions the validator rejects.** The reference interpreter's evaluator threads bindings left to right. On conditions that fail validation (free variables, or variables that are not range-restricted) its verdicts can differ from the satisfaction relation. Nothing proves that the two agree on valid conditions. The conformance run's decision replay tests it on the corpora's traces.
